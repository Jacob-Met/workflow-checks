## Browser finding and correction

The initial JavaScript registered cancellation in a capturing click listener and queued a microtask to refresh controls. In actual Chrome, while a real /api/decision response was held, the existing target handler had set reviewBusy=true but the batch button still displayed as enabled. The waiting status had not yet appeared.

The focused witness recorded:

- Before clicking Download: reviewBusy=true, disabled=false.
- After clicking it: reviewBusy=true, disabled=true, with the waiting message.
- Batch request count before and after that click: zero.

The click-time submission guard therefore remained effective. The defect was the visible control state during a pending save.

The author retained cancellation in capture and moved control refresh to a bubbling listener, after the existing target handler establishes busy state. The unchanged acceptance probe then passed its pending-save group and all ten other groups. Existing review handlers were left intact.

The real browser checks also cover an actual saved per-load ZIP; visible batch selection and identity; actual batch download bytes equal to the native endpoint; retirement after selection changes, cancellation and unsaved note edits; a fresh request following cancellation; selected-identity invalidation; preservation after an unselected refresh; malformed response type; unsafe attachment filename; and inert prototype/markup-looking load IDs. The final browser has no page errors, infrastructure errors or non-loopback page requests.

