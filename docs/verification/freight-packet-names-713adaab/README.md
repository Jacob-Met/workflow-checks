# Freight packet filenames: native receiving evidence

The repair retains a distinct readable HTML packet for every emitted logical load ID on ordinary Windows filesystems. It preserves the existing summary schema, normal portable filenames, monetary results and review writers. Source ownership is [workflow-checks issue #39](https://github.com/Jacob-Met/workflow-checks/issues/39); batch-export issue #37 keeps its separate owner.

## Actual product result

The original source and the repaired source each ran the ordinary CLI against three sets of synthetic input bytes on DESKTOP-LA7CMTA, Windows 10 build 19045, installed Python 3.11.9 and NTFS. Every product process returned zero.

Each case has 18 unchanged input files and 14 report files preserved across the read-only consumer calls. The 31 source files remain unchanged during receiving. The explicit counts, monetary totals, per-packet facts, stop-rule results, flags and settlement projection agree with the corresponding original-source run. ## Invocation and transport

The baseline driver first calls the actual synthetic generator with 8 loads and seed 7, then runs three actual `python -B -m freightpkt run --data ... --out ...` commands. Only the case-pair and NUL fixtures substitute logical ID text in the synthetic inputs. The repaired driver uses the exact original input bytes and retains the original report hash as a pin.

Both drivers run under the existing SSH minec session through the installed Python 3.11 launcher. The driver process uses `py -3.11 -I -S -B -X utf8 receiving-driver.py`; its product subprocesses use the ordinary interpreter and module entrypoint. The source directory, runtime, full argv and relevant environment are in the raw report. The SSH route was ThinkPad RDC to the existing minec Windows SSH endpoint. No credential or connection configuration moved.

ThinkPad output retrieval later timed out. Direct read-only Windows RDC access recovered the already-finished receipt and custody ZIP; no product command was repeated. A PowerShell 5 JSON parsing attempt refused the legitimate case-distinct load-ID keys, and one direct read-only Python lookup returned 1 without output. These observer attempts are retained separately in [transport recovery](continuation/transport-recovery.json); neither is a product qualification failure. Raw report reads and native Get-FileHash agreed on the stated receipt hash.

The original baseline and repaired namespaces are distinct private directories under minec's Temp. Their full paths are retained in the reports and source/input bundles. No existing service or customer data was used.

## What is retained

The four [archives](archives/) total 474,479 bytes and preserve all source, drivers, synthetic inputs, reports, actual generated HTML and the four consumer ZIPs. Their exact sizes and hashes appear in acceptance.json and packet-manifest.json. Readable report/manifests/log projections are byte-for-byte copies of those archives. The base64 transfer envelope (633,833 bytes) is retained on Windows and Mac; its hash is recorded, and the publication retains the exact four original archives.

[Acceptance](acceptance.json) identifies the current four source hashes, both qualification sources, the test-only revision and explicit limits. [Packet manifest](packet-manifest.json) inventories every other published packet file and deliberately excludes its own checksum.

The allocation covers filename components. It does not establish atomic output publication, concurrent-writer safety, hostile output-parent protection, whole-path-length handling, or historical-file cleanup. An output directory must be controlled and stable. Existing filename-sensitive reviews become stale through the unchanged evidence-version contract when a filename changes. No install, payment, live-stage change, migration cutover or firmware operation occurred.
